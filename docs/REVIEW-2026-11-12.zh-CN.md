## 2. P1 详细问题

### RV-01 沙箱启动器经 PATH 解析，工作区内可写目录可劫持并丢弃 profile（安全）

- 位置：`internal/tools/process.go:94`、`:110`、`:128`；对照 `internal/tools/standard_bash.go:541`（bash 本身已钉死为 `/bin/bash`）。
- 证据：`exec.LookPath("sandbox-exec")` / `exec.LookPath("bwrap")` 结果直接作为 `exec.CommandContext` 的可执行文件，而 `PATH` 来自宿主环境并原样保留（`process.go:130`）。子代理实测：把工作区内目录放到 PATH 首位、写入同名伪造脚本后，`workspace-write` 下一条 `echo x > <workspace 外路径>` 成功执行，伪造脚本还收到了完整 Seatbelt profile 参数。
- 影响：默认权限可被模型自行提升为宿主任意路径写，且无需审批。前提是用户启动 dsgo 时 PATH 含工作区内目录（`.venv/bin`、`node_modules/.bin`、`direnv` 的 `bin` 很常见）。Linux `bwrap` 同理。
- 修复：只从固定受信路径解析启动器（`/usr/bin/sandbox-exec`、`/usr/bin/bwrap`，或 `/usr/bin:/bin:/usr/local/bin` 候选表），`EvalSymlinks` 后校验其不在 workspace 内、且不可被当前用户/模型写入（属主或 `access(W_OK)` 校验）；解析失败 fail-closed。禁止使用 `exec.LookPath` 的 PATH 搜索。
- 验证：已确认（隔离复现）。

### RV-02 Linux bubblewrap 缺 `--unshare-pid`，`/proc/<pid>/root` 可绕过只读根绑定（安全）

- 位置：`internal/tools/process.go:115`。
- 证据：argv 为 `--die-with-parent --new-session --ro-bind / / --dev /dev --proc /proc --bind tmp tmp --chdir cwd`，挂载了新的 procfs 却没有私有 PID 命名空间。没有 PID 命名空间时 `/proc/<pid>/root`、`/proc/<pid>/cwd` 解析到目标进程的挂载视图，同 uid 的 harness 父进程通常可被读取，从而绕过 `--ro-bind / /` 的只读属性写入宿主任意路径。上游 `687f282e` 已有「bwrap 私有 PID 命名空间」修复记录，本实现未包含。
- 影响：Linux 上 read-only / workspace-write 的整机写边界被打破，且与 macOS 后端不一致。
- 修复：argv 增加 `--unshare-pid`（置于 `--proc` 之前）；启动前做一次功能探测（`bwrap --unshare-pid --ro-bind / / --dev /dev /bin/true`），探测失败按现有「restricted mode unavailable」fail-closed。
- 验证：疑似（静态确认 + 上游同源修复对照；本机无 bwrap，未实机复现）。

### RV-03 压缩摘要接受 refusal / stop_sequence / pause_turn，拒答文本会替换真实上下文（数据丢失）

- 位置：`internal/agent/compaction_request.go:174-194`；提交点 `:141`。
- 证据：`compactionSummary` 只拒绝 `max_tokens` 与 `model_context_window_exceeded`，其余 StopReason 只要文本非空就作为摘要；随后 `compactAt` 以「更小」为条件提交 CAS。子代理隔离复现：模型返回 `"I cannot assist with that."` + `refusal`/`stop_sequence`/`pause_turn`，三次 `Engine.Compact` 均返回 `nil`，当前 surface 被替换为 checkpoint（含拒答文本），原 user/assistant 从模型可见面消失。没有 un-compact 命令。
- 影响：一次拒答或非正常终止即可把一段真实上下文永久换成一段无信息文本；之后模型把拒答当作「已确立背景」继续工作。
- 修复：`compactionSummary` 只接受 `end_turn`（适配器不回填时允许空串），显式拒绝 `refusal`、`stop_sequence`、`pause_turn`；失败不替换 surface。补非 `end_turn` 的回归。
- 验证：已确认（隔离复现）。

### RV-04 `/resume` 后 `/new`、`/archive` 仍用启动工作区，可能在错误项目甚至父目录里运行（边界）

- 位置：`internal/cli/cli.go:437`（新会话用 `a.flags.cwd`）、`:316`（`a.flags.cwd` 只在启动时覆盖一次）；`internal/cli/commands.go:179`、`:202`。
- 证据：`selectSession` 新建会话固定 `a.store.Create(a.flags.cwd, ...)`；`/resume` 只改 `a.session`，不更新 `a.flags.cwd`。子代理真实二进制复现：先建会话 B（CWD=`wsB`），再用 `--cwd wsA chat` 执行 `/resume B`、`/new`，新会话 `meta.json.cwd` 为 `wsA`；`/archive` 同样。复现示例中启动目录若是 `~/code`（多仓库父目录），新会话沙箱边界就是整个 `~/code`。
- 影响：`Session.CWD` 同时是 `WorkspaceRoot`。错误的 CWD 会把工具沙箱放宽到父目录，模型可修改同级其他项目；skills/AGENTS.md 也来自错误目录。
- 修复：`/new`、`/archive` 使用当前会话的 `CWD`（或 `activeWorkingDirectory`），`/resume` 成功后同步「当前工作区」字段；补 `/resume` 跨 CWD 后 `/new` 的 Main 级测试。
- 验证：已确认（真实二进制复现）。

### RV-05 每个回合对全工作区做两次全量快照，并逐文件重写 blob（性能/磁盘，用户可感知）

- 位置：`internal/artifacts/workspace.go:47-130`（Capture 读取并哈希全部文件）、`:145`（每个文件 `putBlob`）；`internal/cli/artifacts.go:54-105`（`workspaceTurnStarted`/`workspaceTurnFinished` 各一次）；`internal/artifacts/store.go:52-78`（先写临时文件 + fsync，之后才检查 blob 是否已存在）。
- 证据：`Capture` 只排除 `.git`，不排除 `node_modules`、`.cache`、`target`、`dist` 等；对每个文件读取全部内容计算 SHA-256，未超大文件还调用 `putBlob`，而 `write` 在内容寻址命中前已经完成「临时文件 + 写入 + fsync + close」。真实二进制：在本仓库（含 379MB Go 构建缓存，总计 573MB）执行一次失败的 `dsgo run "hi"` 耗时 **16.4s**，stderr 为 `artifact preview unavailable: workspace snapshot exceeds byte limit`；同一命令在小工作区 **0.12s**。
- 影响：普通仓库（`node_modules` 动辄数百 MB）每回合产生数十秒延迟、256MB 上限后 artifacts 整体不可用、且每次快照重写全部 blob 造成大量 fsync 写放大；叠加 RV-36 的磁盘无界增长。这是当前最容易被用户直接感知的问题。
- 修复：(1) `Capture` 复用上一份 Snapshot，仅对新增/变化文件读取与落盘；`putBlob` 先 `Lstat` 目标 blob，命中即跳过（内容寻址无需回读比较）；(2) 排除常见构建/依赖目录并支持 `.gitignore`；(3) 超大文件按 `size/mtime` 直接标记 `Oversized`，不读内容；(4) 达不到上限时返回「部分快照 + warning」，而不是整份 artifacts 失效；(5) 视产品取舍，结束快照可延迟到 `/diff`/`/artifacts` 请求时再做。
- 验证：已确认（真实二进制计时；代码路径确定）。

### RV-06 HTTP MCP 传输死亡不会触发重连，关闭失败还会永久 block 并卡死配置 reload（可靠性）

- 位置：`internal/mcp/client.go:524-532`（`fail` 仅由 `Close` 调用）、`internal/mcp/http_events.go:117-172`（所有退出分支只 `return`）、`internal/mcp/supervisor.go:296-320`（等待 `client.Done()` 与 `ErrIncompleteClose`）、`internal/mcp/http.go:221-254`（DELETE 失败返回错误）、`internal/cli/mcp_connections.go:126-136`（reload 在 `previous.Close()` 失败时 `return`）。
- 证据：HTTP 客户端的 `fail()` 唯一调用点是 `Client.Close()`；stdio 才有 `readLoop`/`cmd.Wait` 触发。`readHTTPEvents` 在 GET 连续失败、`ErrSessionExpired`、405、重试预算耗尽时静默退出，不 `fail`、不告警；supervisor 的 `case <-client.Done()` 对 HTTP 永不成立。子代理 httptest 复现：legacy HTTP 服务关闭 1.5s 后 `status=connected attempts=0`，调用报 `MCP HTTP transport request failed`，没有新的 `initialize`。另一半：`httpTransport.close()` 对 DELETE 的任何失败（连接断开、503）返回错误，supervisor 视为 `ErrIncompleteClose` 进入 `blocked`；`reloadMCP` 又在 `previous.Close()` 失败时直接返回，导致配置轮询每 500ms 失败一次、旧 supervisor 永远留着、新配置永不生效。
- 影响：HTTP MCP 服务器重启/换端口/反代 502 后，整组工具永久失效且无法恢复；一次 DELETE 失败会让该服务器永久不可 reload，只能重启进程。
- 修复：(1) `readHTTPEvents` 在预算耗尽/`ErrSessionExpired` 时调用 `c.fail(...)`，让既有 supervisor 恢复路径生效；`httpCall` 把「传输不可达/会话过期」与「单次请求被拒」区分，前者标记 broken；(2) `httpTransport.close()` 的 DELETE 失败降级为非致命（独立哨兵），`ErrIncompleteClose` 只用于 stdio；(3) `reloadMCP` 先删除旧 entry、best-effort Close，失败只记日志；(4) 所有退出原因写 warning/日志。补「服务器重启」与「DELETE 返回 503」回归。
- 验证：已确认（本地 httptest 复现 + 代码路径）。

### RV-07 缺少 cwebp 时，一张大尺寸透明 PNG 会永久毒化该会话的全部请求（可靠性）

- 位置：`internal/cli/image_projection.go:95-131`（`projectRequestImage` 不处理编解码错误）、`internal/cli/images.go:181`（read_image 落盘）、`internal/attachments/images.go:441-447`（`IMAGE_CODEC_UNAVAILABLE`）。
- 证据：大尺寸带 alpha 图片在请求投影时需要 `cwebp`；`encodeImageWithinBytesAlpha` 直接返回 `IMAGE_CODEC_UNAVAILABLE`，`projectRequestImage` 未降级，错误在 `Model.Stream` 之前冒泡。图片已持久化进历史，之后每个请求都会重放它；`/compact` 也走同一投影且图片通常在保留尾部。子代理复现：2000×2000 半透明 PNG 落盘成功，`PATH` 置空后 `ResolveProjected(...).Stream(...)` 返回该错误，fake model 调用次数 0。
- 影响：`read_image`/`/attach` 一张截图或设计稿（透明通道很常见），该会话此后每一轮、每个子代理都失败；macOS 默认不装 cwebp，用户唯一线索是 `doctor` 的 `image_codecs`，只能装 cwebp 或换会话。
- 修复：(1) `readImage`/`attach` 入库前预检 alpha + 需要缩放的图片，缺编码器直接返回工具错误、不落盘；(2) `projectRequestImage` 用 `errors.As` 识别 `IMAGE_CODEC_UNAVAILABLE`/`IMAGE_CODEC_FAILED`，降级为 `Omit: true` + 文本 handle，保证历史中的「毒图」不再阻塞后续请求；(3) 启动时对官方路由声明 image 但缺 cwebp 给一次性警告。
- 验证：已确认（子代理隔离复现）。

### RV-08 事件日志每次追加/投影全量重读并 JSON 解析，且全程持有全局 `.lock`（性能/可扩展性）

- 位置：`internal/state/store.go:412-429`（`append` 调 `readEvents`）、`:339-390`（逐行 `json.Unmarshal` 校验）、`:118-131`（全局 `.lock` 覆盖读、截断、写、fsync）；重复读示例 `internal/state/context.go:17-31`。
- 证据：主审基准：3000 条 1KB 事件追加总耗时 40.0s（平均 13.3ms，末次 16.5ms），文件 3.6MB；`Messages` 同一日志 15–24ms；子代理基准：8000 条（9.2MB）单次 Append 38ms，其中 23ms 是 `readEvents`。引擎每步会 append 多条事件（step/timing、plan/request、tool/started、tool/finished、tool/result、时间上下文等），并多次调用 `Messages`/`Events`；`withLock` 是进程内/跨进程唯一的全局锁，fsync 期间阻塞所有会话的 list/resume/append。
- 影响：长会话（数万事件）每步秒级卡顿；所有进程的会话操作被串行化；与 RV-05 叠加时启动/回合延迟更明显。不是数据损坏，是明确的 O(n²) 读写放大。
- 修复：(1) 在 `Store` 内缓存每会话 `(inode,size,count,lastSeq)`，append 前 `Stat` 校验后直接 seek 追加并回读最后一条校验，未命中才全量扫描；(2) 拆锁：全局 `.lock` 只保护创建/删除/列举，每会话 `.lock` 保护 append/meta；(3) `Events`/`Export` 仍保留全量严格校验，另提供 `fsck`；(4) `UpdatedAt` 的 meta 写可合并/去 fsync。
- 验证：已确认（主审与子代理基准）。

### RV-10 工具循环在 render/emit/audit 失败与取消路径不补 `tool_result`，也不清理 liveTools

- 证据：`RenderToolResult` 出错、`tc.Emit` 审计出错、`tool/finished` 追加失败都会直接 `return`，跳过 `:511` 的 `endToolExecution` 与 `:519-522` 的 synthetic `tool_result`。子代理复现：工具已成功执行，但历史里只有 `assistant(tool_use)`，没有 `tool/result`；下一次 `Run` 在 `:240-255` 把这次成功执行当作「进程崩溃」补失败结果。取消发生在 render 内时两个 tool_use 都悬挂，与 `:519` 的注释矛盾。

- 验证：已确认（两个隔离复现）。

- 证据：`MaxImagePixels=64_000_000` 只限像素；PNG 16-bit RGBA/GA 解码为 `NRGBA64/RGBA64`（8 B/px），64M px ≈ 512MiB；`compression` 允许两路并发。子代理用真实 `SaveImage` 复现：2000×2000 16-bit RGBA（压缩后 233KB）`TotalAlloc` 62.9MiB，按 64M px 折算约 1GiB 分配。
- 影响：一张 16-bit PNG 或压缩炸弹即可让进程 OOM；小内存机器/容器更明显。
- 修复：解码前按格式头计算字节上界（PNG bit depth×color type×interlace、JPEG 分量、WebP 帧、GIF 画布）、设置 `MaxDecodedImageBytes`（如 256MiB）直接拒绝；或按字节设限；压缩槽位降为 1 或按字节预算。
- 验证：已确认（子代理实测）。

### RV-33 括号粘贴把 ESC 交给转义解析，截断 UTF-8 会卡死输入框，含终止符会提前提交

- 位置：`internal/tui/lineedit.go:283`、`:387`、`:473`。
- 证据：paste 模式下 ESC 交给 `escape()`；`insertUTF8` 的 `FullRune` 循环会把终止符开头的 ESC 当续字节读走，随后 `[201~` 被插入。子代理复现：粘贴 `ok\x1b[200~\xe4\x1b[201~` 后回车 → `line="ok[201~\n"`、`done=false`、`paste=true`，回车只换行、无法提交；粘贴内容含 `\x1b[201~` 会提前结束并提交 `/quit\r`。
- 影响：粘贴 Latin-1/截断文本后输入框卡死；恶意剪贴板内容可绕过 bracketed-paste 保护当命令执行。
- 修复：`insertUTF8` 只消费 UTF-8 续字节（`b&0xC0==0x80`），非续字节 unread 并丢弃非法前导；粘贴态改为独立缓冲/状态机，粘贴期间不经 `key()` 分发。
- 验证：已确认（子代理复现）。

### RV-34 后台/其他会话的审批与提问会接管前台输入，但无会话归属且 Ctrl+C 不能取消

### RV-37 macOS 沙箱保留控制终端并允许写 `/dev/tty`，read-only 也能注入终端/读键盘

- 位置：`internal/tools/process.go:102`、`internal/tools/process_unix.go:11-23`。
- 证据：Seatbelt profile 显式 `allow file-write* (literal "/dev/tty")`；`configureProcess` 只 `Setpgid`、没有 `Setsid`，子进程仍持有 harness 的控制终端；`(allow default)` 又放行 `/dev/tty` 读。Linux 分支显式加了 `--new-session`，macOS 无等价处置。

- 修复：`configureProcess` 增加 `Setsid: true`（新会话无控制终端，pgid==pid）；删除 profile 中的 `/dev/tty` 放行，只留 `/dev/null` 与 `/dev/fd/[0-9]+`。
- 验证：疑似（代码确认；本机无 TTY，Seatbelt 运行时被外层沙箱阻断）。

## 6. 经核对不构成问题或设计合理的部分

- **state 锁顺序**：`withLock` 全局锁 + `.turn.lock` 非阻塞（`lockFile(..., false)` 立即 `ErrBusy`）不会形成「运行回合持会话锁再取全局锁」的反向环；未发现经典死锁。RV-08 是性能问题，不是死锁。
- **webtools SSRF 防护**：`dialPublic` 先解析、再按 IP 拨号并拒绝私网/环回/链路本地/文档网段；`Proxy: nil`；跨源重定向一律拒绝。未发现十进制 IP/DNS rebinding 绕过（这是全仓最好的一处）。
- **文件写入边界**：`write`/`edit` 走 `os.Root`、拒绝目标符号链接、写入前按内容哈希二次校验 observation、创建用 `link` 的 create-if-absent、更新用 rename；未发现路径穿越或硬链接写穿。
- **Anthropic SSE 解析**：处理 TCP 分片、BOM、注释、多行 `data`、CRLF；`message_stop` 前不把 EOF 当成功；测试覆盖充分。
- **输入 broker**：单一物理 reader、park/takeover、取消后 drain 迟到输入、私有问答与 composer 隔离，测试较强；本次未发现新的输入错配（RV-33/RV-34 属 TUI 与提示归属，不是 broker 本身）。
- **凭据持久化顺序**：`config`/`auth` 在 `WithEnvironment()` 之前处理，环境变量凭据不会因普通配置编辑落盘；`Masked()` 对 API key/account/provider profiles/env/headers 的核心遮蔽有效（RV-42 是 args/URL 边角）。
- **模型错误文本**：`responseError` 只保留稳定 code/status，不显示供应商文本或 URL；replay identity 用 HMAC 绑定协议/端点/凭据，未发现跨 provider 误用。
